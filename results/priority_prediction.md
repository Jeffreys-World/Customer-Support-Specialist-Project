# Priority prediction — measured ceiling

Generated by `python -m prediction_model --write` over **8,469 tickets** from `classified_tickets.json`. Every split is seeded (`random_state=42`), so these numbers reproduce exactly.

> **Headline: no feature set beats guessing.** The best held-out accuracy of any model tried is **26.1%** (`text`), against a **25.0%** chance baseline and a **25.9%** majority-class baseline. That is +0.2 points on 1,694 held-out tickets, where one standard error is 1.1 points — so it is noise, not an edge. This is a property of the dataset, not of the models.

## Why this was measured instead of shipped

`IMPLEMENTATION_PLAN.md` Phase 2 proposed a RandomForest over `[Keyword_Urgency_Score, Days_Open]` and a `Predicted_Priority` column merged into the dashboard. Before writing that, two facts had to be checked:

1. `results/evaluation.md` §3 had already shown the priority label is independent of the ticket text. Re-measured here with the same helper: `chi2 = 40.9` on `45 dof`, Cramér's V = `0.040`. A chi-square at or below its degrees of freedom is what independence looks like.
2. The proposed snippet fit and predicted on the same rows, so it would have reported a train-set score as if it were accuracy. The gap column below is what that would have hidden.

## Results

| Feature set | Features | Held-out acc. | 5-fold CV | Macro F1 | Train acc. | Gap |
|---|---|---|---|---|---|---|
| `plan-features` | 2 | **24.9%** | 26.4% | 0.249 | 70.1% | +45.2 pts |
| `tabular` | 59 | **25.9%** | 26.6% | 0.258 | 85.2% | +59.3 pts |
| `text` | TF-IDF 1-2gram | **26.1%** | 25.9% | 0.261 | 62.2% | +36.1 pts |

Baselines: **25.0%** chance (4 near-balanced classes), **25.9%** always-guess-the-majority-class. Class counts: Critical 2,129, High 2,085, Low 2,063, Medium 2,192.

Reading the table:

- **`plan-features`** is exactly what Phase 2 specified. Note the train column: that is the ~70% the original snippet would have printed, from a model whose real accuracy is at chance. A RandomForest given a near-unique numeric feature (`days_since_purchase`) memorises the training rows and generalises nothing.
- **`tabular`** adds every operational column — channel, product, ticket type, status, CSAT, the scorer's own category and signal count. No improvement.
- **`text`** reads the ticket subject and body directly. If the label were recoverable from anything in this dataset, this is where it would show up. It does not, which is the chi-square result restated as a learning curve.

## `Days_Open` could not be computed

Phase 2's second feature does not exist in this dataset. There is no ticket-creation timestamp — the only date is `purchase_date`, which precedes every ticket by years. Measured from the fixed reference date this file uses, `days_since_purchase` spans roughly 1,700–2,400 days, so the plan's `Days_Open > 5` overdue test would have been true for every row in the dataset. It is kept as a feature here only to reproduce Phase 2 faithfully.

## What was not done, and why

No `Predicted_Priority` column was merged into the dashboard. At the accuracy above it would have been a random number sitting beside a real one, in a console whose own Data integrity panel tells the user this label is not learnable. The rule-based scorer stays the product: it is deterministic, it explains every call it makes, and its Critical-class safety net is a guarantee about vocabulary rather than a prediction — which is exactly the property that survives a dataset whose labels carry no signal.

The honest use for a model here would be a label the data can actually support. This dataset does not have one: the bodies are templated from 16 subject lines, and the resolution notes are generator filler (see the Dashboard's Data integrity panel).
